# AGENTS.md — `HiveMind-cli`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

HiveMind-cli is a terminal client for HiveMind: type an utterance, watch the
response on the bus, with a curses split-pane UI (`--no-curses` for plain
stdin/stdout). It is the thinnest satellite in the HiveMind spectrum — no
microphone, no speaker, no wake word, no local processing at all. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the wire
client library it builds on is
[hivemind-bus-client](https://github.com/JarbasHiveMind/HiveMind-bus-client).
Siblings on the same spectrum: hivemind-mic-satellite, HiveMind-voice-relay,
HiveMind-voice-sat.

## Layout / build / test

- Package module: `hivemind_cli_terminal/`. Tests live in `tests/` (only
  `tests/e2e/` exists — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[e2e]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. The e2e suite
  boots a real `hivemind-core` master in-process via `hivescope` (loopback
  WebSocket) and drives the real terminal client over a real bus client; only
  stdin/stdout is mocked. `conftest.py` warns loudly on any XPASS — treat that
  as a signal to flip the corresponding `xfail` marker, not to ignore.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why).
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Everything in `pyproject.toml` (deps, metadata, version). Never install from
  git — depend on a published PyPI alpha. There is no `requirements.txt`; do not
  add one.
- Apache-2.0. Do not add GPL/AGPL dependencies.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is an end-user satellite app, not a wire-protocol implementation: it
  speaks HiveMind over `hivemind-bus-client`, it does not define the protocol.
  Keep it on the bus-client 2.x stack (`ovos-bus-client>=2.0`).
- Bad credentials must fail fast. Do not add silent retry/reconnect-forever
  loops around a rejected access key; a refused key is a terminal condition the
  user must be told about, not something to paper over.
- Named-session semantics belong to the server (`hivemind-core add-client`);
  this client only ever holds a key and password it was given at invocation —
  do not add local credential caching or persistence beyond what the user
  passes on the command line, and never hardcode a secret in source, tests, or
  docs.
- The two UI modes (curses and `--no-curses` plain) must stay behaviourally
  equivalent for utterance send/receive; changes to one need the equivalent
  check in the other, and the curses-unavailable-at-import fallback to plain
  mode must keep working.
- The README quickstart (`hivemind-core add-client` → `hivemind-cli
  --access-key ... --host wss://...`) must stay accurate — if a flag or default
  changes, update the README and `docs/` in the same PR, not as a follow-up.
